## Как читать

## Очередь миграций

Миграции попадают в main по одной. Очередь держит открытый PR с меткой «миграция»: такой PR в репозитории один.
1. Пока задача в работе, миграции делаются как обычно (`pnpm db:generate`, ручные — `--custom`). Номер миграции окончательный только после слияния.
2. Когда всё остальное готово (тесты, отчёт ревьюеров, описание PR), сессия проверяет, нет ли открытого PR с меткой «миграция».
	- Если есть — ждёт его слияния (подписка на этот PR), а пока делает правки без базы.
	- Если нет — ставит метку на свой PR и сразу проверяет ещё раз. Если метка оказалась у двух PR, её оставляет PR с меньшим номером, второй снимает.
3. С меткой сессия обновляет ветку с main — слиянием, не rebase (force-push запрещён). Если в main появились новые миграции, свои пересоздаются после них:
	- сохранить в сторону SQL своих ручных миграций;
	- `git fetch origin main && git merge origin/main`, затем `git restore --source=origin/main --staged --worktree packages/db/migrations`: файлы, которые есть только в ветке, исчезают, а журнал и конфликт в нём становятся как в main. Удалять файлы миграций и править `meta/_journal.json` руками нельзя — не дают хуки;
	- заново `pnpm db:generate`; ручные миграции — заново через `--custom` с сохранённым SQL;
	- применённые миграции из main не трогать: не дадут хук и проверка `check` (scripts/check-protected.mjs);
	- если хук остановил — не обходить, а спросить в треде «П: Архитектура и план разработки».
4. `pnpm check` и push. Пока метка стоит, схему не менять.
5. Метка уходит вместе со слитым PR. Если PR застрял (красная проверка, которую быстро не починить, замечание ревью), метку снять, чтобы не держать очередь, и поставить заново, когда PR готов.
6. После слияния — сообщить в тред «П: Архитектура и план разработки» номера миграций и таблицы: я сверяю DevBuhUchet.kg/db/schema.json.

Если правило нарушат, ошибка всё равно не попадёт в main. Две миграции с одним номером конфликтуют в `meta/_journal.json` и снимке, а автослияние не сливает ветку, отставшую от main. CI проверяет, что `pnpm db:generate` после схемы ничего не создаёт.

## Как не мешать друг другу

- Свои папки. Поток правит код своих модулей: `packages/<пакет>/src/<модуль>`, `apps/web/src/<модуль>`, свои схемы `packages/db/src/schema/<модуль>.ts`. Общие части (`packages/ui`, общий список, оболочка, шкала статусов, история) — только небольшими добавлениями. Переделка общего — отдельным PR. `withOrgContext` и функции контекста RLS (`app.current_org_id()`, `app.current_user_id()`) меняются только отдельным PR, даже немного; о нём сессия пишет в тред «П: Архитектура и план разработки», чтобы остальные потоки обновили ветки.
- Общие файлы-списки — одна строка на модуль, по порядку модулей ТЗ, а не в конец. Это маршруты в `packages/api/src/app.ts`, экспорт в `schema/index.ts`, словарь в `l10n/texts.ts`, список модулей оболочки, `HISTORY_ENTITIES` и `HISTORY_ACTIONS`, шкалы статусов. При конфликте оставить обе строки.
- Тексты словаря — в своём `packages/domain/src/l10n/<модуль>-texts.ts`.
- Демо-данные — своим файлом `packages/db/src/seed/demo-<модуль>.ts`, в `demo.ts` только вызов.
- Номера новых пунктов `docs/deviations.md` и `docs/decisions.md` — с буквой потока по метке Issue задачи: «Г-1», «Г-2»… (задачи потока Е — «Е-1», в какой бы сессии они ни шли). Работа вне потоков (общие правила, общие задачи, просьбы заказчика без Issue потока) — буква «О». Счёт свой у каждой буквы, отдельно для deviations и для decisions; следующий номер — после наибольшего своего в main и в своих открытых PR. Номер не меняется после слияния, поэтому на него можно ссылаться в вопросе заказчику, в коде и в acceptance-map сразу.
	- Формат: в deviations — заголовок «## Г-1. <что>», в decisions — «Г-1. **<что>.** …» после пустой строки (иначе пункт приклеится к подпунктам предыдущего); ссылка — «docs/deviations.md п. Г-1». Пункт — в конец файла; при конфликте оставить оба пункта.
	- Пункты 1–49 deviations и 1–42 decisions, уже слитые в main к 27.10.2026 (п. 49 и 42 — «Учётные записи» потока Д, PR #105), сохраняют свои номера. Правило в репозитории — CLAUDE.md и скилл spec-deviation (PR #109).
	- Пункт, который поток уже записал с общим номером, но ещё не слил (27.10.2026: п. 49 и 50 у потоков В, Г и Д), получает номер своего потока; ссылки в своём PR правятся. Если вопрос заказчику уже задан с прежним номером — одной строкой в своём треде сказать новый номер.
- `docs/acceptance-map.md` — свой раздел «## Этап 2. <задача>» в конце.
- `pnpm spec:sync` — только отдельным PR без другой работы, кроме того, что синхронизация ломает (наполнение, тесты); остальные потоки потом обновляют ветки.
	- Делает тот поток, который заметил, что spec/ отстал от прототипа, — договорившись с тредом «П: Архитектура и план разработки»; после слияния тред плана оповещает остальные потоки.
	- 27.10.2026: синхронизацию с v58 (6b82955) до v59 сделал поток Д (PR #113).
- Ветку держать свежей: обновлять с main слиянием (не rebase: force-push запрещён) при каждом сообщении автослияния «ветка отстала» и перед очередью миграций.
- Правило стыков. Если задача добавляет свой кусок на экран другой задачи (вкладку карточки контрагента, плашку или значок списка, шаг Базы знаний, источник Файлового менеджера, вкладку справочника в Админке), а этого экрана ещё нет:
	- задача делает свой кусок (компонент, метод API, тест) и не показывает его на экране;
	- метод API при этом доступен по сети сразу, поэтому с первого дня он с проверкой входа, правом с областью, схемой ответа, ответом 400 на неверные данные и тестами;
	- подключает его задача экрана, когда до неё дойдёт;
	- если экран уже есть, задача подключает свой кусок сама.
- Пункт приёмки, которому нужны обе задачи стыка, закрывает та, что слита позже, и записывает это в docs/acceptance-map.md.
- Шаги Базы знаний (стык с 2.30, слита 27.10.2026, PR #111; docs/decisions.md п. Г-2 продукта). Каждая задача модуля, слитая после неё, сама:

	- добавляет «Перейти» в `KB_GO` (`apps/web/src/kb/kb-go.ts`);
	- добавляет свой модуль в `KB_READY_MODULES`.
	- Шаг «Сделать», который засчитывается сменой статуса (свой переход на шкале в `status_history`, откаты не считаются), — вид правила `status` в `KB_STEP_RULES`; его разбирает `kbDoneFacts` (`packages/db/src/kb.ts`). Появляется с 2.23 (PR #117: шаги задач `tdone`, `tconf`), пригодится отчётам (2.14).
	- Программа администратора платформы в 2.30 пустая: шаги экранов Админки добавляют задачи потока Д; шаги уже слитых экранов Админки — первая задача Д, слитая после 2.30.
