#### План разработки Buhuchet.kg: архитектура и работа через Claude Code

Этот документ отвечает на три вопроса: на чём пишется рабочий продукт, как устроить его так, чтобы в любой момент переехать с Vercel и Supabase на обычные VPS/VDS, и как вести всю разработку через Claude Code. Код по этому документу ещё не пишется. Всё, что вы ещё не подтверждали, помечено **(по умолчанию)**. Вопросы к вам собраны в конце, самые важные первыми.

##### Коротко: главные решения

- Сверка 25.10.2026: план актуален для прототипа v57; добавлены страница контрагента по ссылке (с v56), подтверждение сдачи вместо «Принят» (с v56), обновлены сроки

- Стек первого выпуска (на Vercel и Supabase) остаётся прежним: Next.js на Vercel Pro, API на Hono, Supabase Pro (PostgreSQL и хранилище файлов); домен buhuchet.kg подключается к Vercel напрямую, без Cloudflare (ваш ответ 21.10.2026)
- Но от Vercel и Supabase берём только то, что есть на любом сервере
	- От Supabase — обычную базу PostgreSQL и хранилище файлов по протоколу S3; вход, «живые» обновления, функции Supabase и библиотеку supabase-js не используем
	- От Vercel — только запуск Node.js-приложения и вызов задач по расписанию; специальные сервисы Vercel (Edge, KV, Blob, Server Actions для данных) не используем
- Всё, что зависит от поставщика, спрятано за пятью «переходниками» в коде: база, файлы, расписание, отправка в Telegram, настройки окружения; при переезде меняются только они и переменные окружения
- С первого дня приложение запускается и на Vercel, и в Docker на обычном сервере; проверка «собирается и проходит тесты в Docker» стоит в каждой проверке кода, поэтому переносимость не может незаметно сломаться
- Три изменения к ранее принятому стеку (подробно в разделе «Что меняем в ранее принятом стеке»)
	- Вход и сеансы — своя таблица пользователей и свои сеансы, без Supabase Auth и без JWT Supabase
	- Защита данных организаций в базе (RLS) — через настройку сеанса базы «текущая организация», а не через функции Supabase
	- API — отдельный пакет Hono, который в MVP встроен в Next.js, а на VPS может работать отдельной программой
- Разработка — через Claude Code по модулям: одна задача = один кусок модуля = одна сессия Claude Code = одна проверенная правка; источник истины — ТЗ и прототип, логика прототипа служит эталоном для тестов

##### Архитектура

- **Общая схема**
	- Браузер (ПК и телефон) → buhuchet.kg (HTTPS и защиту от атак даёт Vercel) → веб-приложение Next.js → API на Hono → PostgreSQL и хранилище файлов
	- Браузер никогда не обращается к базе и хранилищу напрямую: всё идёт через API, который проверяет вход, организацию и права
	- Telegram-бот — вебхук в том же API; задачи по расписанию (создание отчётов, напоминания, сводки, отправка очереди уведомлений) — тоже маршруты API, которые вызывает планировщик
	- Отдельный процесс «worker» (фоновый исполнитель) есть в коде с первого дня; на Vercel его роль играет вызов по расписанию, на VPS он работает постоянно **(по умолчанию)**
- **Части приложения**
	- **Веб-интерфейс (apps/web)** — Next.js (App Router), React, TypeScript, Tailwind CSS
		- Интерфейс за входом работает как обычное одностраничное приложение: страницы берут данные из API, а не из базы напрямую
		- Server Actions и прямые запросы к базе из компонентов не используются, чтобы интерфейс не был привязан к серверу Next.js **(по умолчанию)**
		- Списки (UnifiedDataGrid) — на TanStack Table, загрузка и кэш данных — TanStack Query, формы — React Hook Form со схемами Zod **(по умолчанию)**
		- Все тексты интерфейса — в словаре (модуль «Локализация»), не в коде
		- Сборка `output: "standalone"`: тот же Next.js запускается на Vercel и в Docker без изменений
	- **API (packages/api)** — Hono с @hono/zod-openapi
		- Каждый метод описан схемой Zod: проверка входных и выходных данных, документация OpenAPI строится сама
		- Общий промежуточный слой: вход → организация → права (39 прав с областью «Свои / Все контрагенты») → запись в историю
		- В MVP монтируется в Next.js одним catch-all роутом `app/api/[[...route]]/route.ts`
		- На VPS тот же пакет можно запустить отдельно через @hono/node-server, ничего не переписывая
		- Интерфейс вызывает API через типизированный клиент Hono, поэтому изменение метода сразу видно в интерфейсе как ошибка типов
	- **Бизнес-правила (packages/domain)** — чистый TypeScript без базы, сети и фреймворков
		- Сроки и перенос по производственному календарю, создание отчётов по назначению, шкалы статусов и откат, подбор отчётов по режиму, статусам, основаниям и ГКЭД, правила ГКЭД (ст. 419), тариф Соцфонда и СПиНО, деньги контрагентов и остатки, подсчёт уровня обучения, показатели
		- Это самая важная и самая проверяемая часть: здесь больше всего тестов
		- Источник правил — ТЗ и файлы прототипа src/js/core (derive.js, gked.js, socfund.js, reference.js) и src/js/modules
	- **База (packages/db)** — схема таблиц, миграции, начальное наполнение
		- ORM — Drizzle: схема на TypeScript, миграции — обычные SQL-файлы, работает с любым PostgreSQL **(по умолчанию)**
		- Подключение — драйвер postgres.js через пул соединений; в Supabase — через его пул (Supavisor) в режиме транзакций
	- **Переходники (packages/adapters)** — всё, что зависит от поставщика
		- `storage` — файлы: загрузка, временная ссылка на скачивание, удаление; один драйвер S3 (Supabase Storage по S3, позже MinIO или Cloudflare R2)
		- `scheduler` — кто будит фоновые задачи: Vercel Cron в MVP, cron или worker на VPS
			- И Vercel Cron, и worker раз в минуту вызывают один маршрут `/api/cron/tick`; какие задачи пора запускать и защита от повторного запуска — в нашем коде, по таблице `scheduler_runs` (решение этапа 0, 25.10.2026)
		- `telegram` — отправка сообщений и приём вебхука
		- `config` — все переменные окружения в одном месте, проверены Zod при запуске; приложение не стартует без нужных настроек
		- `clock` — «сейчас» по Бишкеку; в тестах время подменяется (как в прототипе даты демо зафиксированы на 18.10.2026)
	- **Общие схемы (packages/shared)** — схемы Zod и типы, которые используют и API, и формы интерфейса
	- **Фоновый исполнитель (apps/worker)** — небольшая Node.js-программа, которая раз в минуту вызывает те же функции, что и маршруты расписания; на Vercel не запускается **(по умолчанию)**
- **Данные и разделение организаций**
	- Каждая таблица с данными организации имеет столбец `org_id`; один пользователь — одна организация
	- Две линии защиты
		- Первая — API: каждый запрос знает пользователя, организацию и права, и выбирает данные только своей организации и своей области
		- Вторая — база: политики RLS по `org_id`; API в начале каждой транзакции задаёт `SET LOCAL app.org_id = …` и `app.user_id = …`, а политики сравнивают с ними
		- Приложение подключается к базе отдельной ролью без права обходить RLS; служебные задачи по расписанию проходят по организациям явно, по одной **(по умолчанию)**
		- Так RLS работает на любом PostgreSQL, а не только в Supabase
	- Деньги хранятся целым числом в тыйынах (bigint), на экране — «1 250,50» сом **(по умолчанию)**
	- Даты сроков — тип `date`; дата и время — в UTC, показываются и считаются «сегодня» по Бишкеку (UTC+6)
	- История изменений — одна таблица аудита: кто, когда, что было, что стало; пишется в той же транзакции, что и изменение
	- Одновременная правка — у записей номер версии; при сохранении устаревшей версии API отвечает «запись изменена другим пользователем»
	- Поиск по спискам — средствами PostgreSQL (pg_trgm), без внешних поисковых сервисов **(по умолчанию)**
	- Структура таблиц выводится из demoDB.json и refDB.json прототипа: их разделы (contractors, reports, moneyOps, history, tasks, feePayments, projects, files, indicators, indicatorValues, kbProgress, telegramLog и справочники refDB) — это черновик модели данных
	- refDB.json и gkedDB.json становятся начальным наполнением справочников платформы; demoDB.json — демо-организацией на тестовом стенде
- **Вход и сеансы**
	- Своя таблица пользователей: логин (уникален на платформе), хеш пароля argon2id, признак блокировки, привязка Telegram
	- Сеанс — случайный токен в защищённой cookie (HttpOnly, Secure, SameSite=Lax), в базе хранится его хеш; выход и смена пароля удаляют сеансы
	- Защита от подбора пароля и лимит «3 кода в час» — счётчики в PostgreSQL, без внешних сервисов **(по умолчанию)**
	- Восстановление пароля одноразовым кодом в Telegram — как в ТЗ
- **Файлы**
	- Хранилище S3: в MVP — Supabase Storage через его S3-доступ; на VPS — MinIO или Cloudflare R2 **(по умолчанию)**
	- Путь файла: `org/<org_id>/<раздел>/<id>`; в базе — описание файла (имя, размер, тип, кто загрузил, к чему относится)
	- Скачивание — только по временной подписанной ссылке после проверки права; прямого доступа нет
	- Разбор PDF «Из свидетельства и выписки» — на сервере, в первом выпуске, как в ТЗ (в прототипе — только в браузере и без сканов)
		- Сначала читается текстовый слой PDF (pdfjs-dist в Node.js)
		- Если текста нет (скан или фото) — OCR на русском и кыргызском: страница переводится в картинку (pdfjs-dist и @napi-rs/canvas), текст распознаёт Tesseract (tesseract.js с языковыми файлами rus и kir) **(по умолчанию)**
		- Всё работает внутри нашего приложения, файлы во внешние сервисы не отправляются; один и тот же код работает на Vercel и на VPS, языковые файлы лежат в репозитории
		- Разбор идёт задачей в очереди (таблица заданий в PostgreSQL): на Vercel задание выполняется сразу в отдельном вызове API, на VPS — в worker; пользователь видит «Читаем документ…» и затем форму **(по умолчанию)**
		- Лимит времени на один документ — 60 секунд **(по умолчанию)**; не успели или не распознали — «Не удалось прочитать документ. Заполните форму вручную», как в ТЗ
		- Варианты подписей полей и правила хранятся в настройках платформы (ведёт администратор платформы), а не в коде; неудачные распознавания пишутся в журнал без содержимого документа
		- Тесты: набор образцов свидетельств и выписок (с текстом и сканы) с ожидаемыми полями; в репозиторий кладутся только обезличенные образцы **(по умолчанию)**
- **Excel**
	- Загрузка и выгрузка (контрагенты, показатели, справочники платформы с предпросмотром изменений) — библиотека ExcelJS на сервере: шаблоны с защищёнными ячейками, предзаполненные значения **(по умолчанию)**
	- Разбор загрузки идёт в два шага, как в прототипе: предпросмотр (новые, изменённые, без изменений, ошибки), затем подтверждение
- **Уведомления в Telegram**
	- Очередь исходящих сообщений — таблица в PostgreSQL со статусами «ожидает», «отправлено», «ошибка», повторами и паузами под лимиты Telegram
	- Планировщик раз в минуту будит обработку очереди, раз в сутки — создание отчётов и напоминания 7 и 3 дня и в день срока, по понедельникам — сводку
	- Любая задача по расписанию безопасна при повторном запуске: досоздаёт только недостающее (уникальные ключи в базе)
- **Страница контрагента по ссылке (с прототипа v56)** — единственная часть системы, открытая без входа, поэтому к ней отдельные требования
	- Адрес buhuchet.kg/<адрес организации>/inn/<ИНН> — отдельный раздел Next.js вне входа в программу
		- Адрес организации нельзя выбрать из списка занятых слов (api, admin, login, test, www, inn и другие адреса самой программы), чтобы ссылки контрагентов не пересекались с адресами программы **(по умолчанию)**
	- Отдельная группа методов API без входа: только чтение, только один контрагент и только разделы, разрешённые учётной политикой и карточкой; скрытые разделы не приходят в ответе API вовсе, а не только прячутся на экране
	- Код доступа из 6 цифр хранится в базе хешем; после верного кода браузер получает отдельную cookie страницы на 30 дней, привязанную к контрагенту и номеру версии кода; «Сменить код» увеличивает номер версии, и все запомненные браузеры сразу теряют доступ
	- Лимиты: 5 неверных кодов подряд на ссылку — 15 минут перерыва, как в ТЗ, плюс общий лимит с одного адреса IP по всем ссылкам: 30 неверных кодов в час, затем перерыв на час, как в ТЗ **(по умолчанию)**; счётчики в PostgreSQL
	- Выключенная страница, неизвестный ИНН и архивный контрагент дают один и тот же ответ «Страница недоступна», чтобы по ответу нельзя было узнать, есть ли такой ИНН
	- Страница не индексируется (заголовок noindex и robots.txt) и не кэшируется; каждое открытие пишется в историю контрагента
	- Отдельный набор тестов безопасности: чужой ИНН, старый код после смены, перебор кодов, скрытые разделы, архивный контрагент
- **Наблюдение и резервные копии**
	- Ошибки — Sentry (работает с Vercel и с VPS) **(по умолчанию)**
	- Журнал — структурированный вывод pino в стандартный вывод: на Vercel его собирает Vercel, на VPS — journald или Docker
	- Проверка доступности — внешний сервис раз в минуту (например, Better Stack или UptimeRobot) **(по умолчанию)**
	- Резервные копии
		- Ежедневные копии Supabase (Pro, 7 дней)
		- Плюс своя ночная копия `pg_dump` и копия файлов в Cloudflare R2 через GitHub Actions — независимо от Supabase **(по умолчанию)**
		- Раз в месяц копия восстанавливается на чистый PostgreSQL в Docker и прогоняются тесты: так проверяются и копии, и готовность к переезду
- **Регион**
	- Supabase и функции Vercel — в одном регионе (Франкфурт, eu-central-1 / fra1), чтобы каждый запрос к базе не летал между континентами; хранить данные в КР пока не требуется (ваш ответ 21.10.2026)
	- Это требование к рабочему сайту (buhuchet.kg): Supabase Pro во Франкфурте (eu-central-1), функции Vercel — fra1
	- Тестовый стенд (test.buhuchet.kg) — исключение: на бесплатном Supabase город выбрать нельзя, проект buhuchet-test встал в Ирландии (eu-west-1), поэтому функции Vercel стенда стоят в Дублине (dub1), рядом с его базой; заказчик решил оставить так 25.10.2026 (PR #24 и docs/deviations.md п. 1 в kutya001/Buhuchet.kg)
	- Скорость стенда поэтому может немного отличаться от рабочего сайта; для приёмки функций это не важно, нагрузочная проверка этапа 3 делается на рабочем проекте во Франкфурте **(по умолчанию)**
- **Домен buhuchet.kg**
	- Решено 21.10.2026: домен сразу подключается к Vercel, без Cloudflare
		- Сайт открывается по адресу buhuchet.kg; HTTPS-сертификат и защиту от атак даёт сам Vercel
	- Как подключаем (домен куплен на cctld.kg) **(по умолчанию)**
		1. В Vercel добавляем домены: buhuchet.kg и www.buhuchet.kg (рабочий сайт), test.buhuchet.kg (тестовый стенд); Vercel показывает, какие записи DNS нужны
		2. В личном кабинете cctld.kg, в настройках DNS домена, создаём эти записи: для buhuchet.kg — запись A с адресом, который показал Vercel, для www и test — записи CNAME на адрес, который показал Vercel
		3. Серверы имён (NS) не меняем: DNS остаётся у cctld.kg, а не у Vercel, чтобы при переезде домен не был привязан к Vercel
		4. Ждём, пока Vercel покажет «Valid Configuration» у каждого домена (обычно от нескольких минут до нескольких часов); HTTPS включится сам
		- Если в кабинете cctld.kg нет раздела записей DNS (услуга DNS не подключена), её включают там же или пишут в поддержку cctld.kg **(уточнить при подключении)**
	- При переезде на VPS
		- В кабинете cctld.kg запись A меняется на адрес VPS, записи www и test — на тот же адрес
		- Защиты от атак у обычного VPS нет; тогда можно бесплатно подключить Cloudflare (сменить NS в кабинете cctld.kg: «Доменные имена» → «Мои доменные имена» → «Редактировать» → «Обновить»), но это решение на момент переезда, не сейчас **(по умолчанию)**
	- Своё резервное хранилище для ночных копий — Cloudflare R2 или любое другое S3-хранилище; для него не нужно переносить домен **(по умолчанию)**

##### Как избежать привязки к поставщику

- **Правила для кода (записываются в CLAUDE.md и проверяются автоматически)**
	- Нельзя подключать `@supabase/*` и `@vercel/*` нигде, кроме packages/adapters; проверяет правило ESLint `no-restricted-imports`
	- Нельзя использовать в SQL функции Supabase (`auth.uid()`, `auth.jwt()`, схему `storage`), Edge Functions, Realtime, pg_cron
	- Нельзя использовать Edge Runtime Next.js и Server Actions для работы с данными
	- Приложение не пишет файлов на свой диск: всё через `storage`; поэтому его можно запускать в нескольких копиях
	- Все настройки — только из переменных окружения через `config`; никаких адресов и ключей в коде
	- Расширения PostgreSQL — только те, что есть в обычном PostgreSQL (pg_trgm, pgcrypto, citext)
- **Постоянная проверка переносимости**
	- В репозитории `docker-compose.yml`: PostgreSQL, MinIO, приложение, worker — это и есть будущий VPS
		- Официальные образы MinIO больше не публикуются в Docker Hub и quay.io, поэтому в docker-compose.yml и docker-compose.prod.yml стоит сборка сообщества pgsty/minio с закреплённой версией (решение этапа 0, 25.10.2026; подробно — docs/decisions.md репозитория продукта)
		- Код говорит с файлами только по S3, поэтому MinIO на VPS при желании заменяется на Cloudflare R2, Garage или SeaweedFS без правок кода
	- Локальная разработка и все тесты идут на обычном PostgreSQL и MinIO, а не на Supabase
	- В каждой проверке кода (GitHub Actions) собирается Docker-образ и прогоняются сквозные тесты против docker-compose
	- Отдельная команда `pnpm check:portability` ищет запрещённые подключения и SQL; её запускает и проверка кода, и хук Claude Code
- **Что именно заменяется при переезде**
	- Vercel → Docker-образ того же Next.js на VPS за обратным прокси Caddy (HTTPS сам) или nginx
	- Vercel Cron → worker в docker-compose или системный cron, который вызывает те же маршруты с секретным ключом
	- Supabase PostgreSQL → PostgreSQL 16+ в Docker или отдельно установленный; переносится `pg_dump` / `pg_restore`
	- Supabase Storage → MinIO (сборка pgsty/minio) на VPS, Garage или SeaweedFS, либо Cloudflare R2; файлы переносятся `rclone sync` по S3
	- Supabase-копии → своя ночная копия (уже есть с первого выпуска) и restic или borg на второй сервер
	- Домен остаётся на cctld.kg: меняется только адрес сервера в записях DNS

##### Переезд на VPS/VDS

- **Можно переезжать частями**
	- Только файлы: поменять переменные S3 на MinIO или R2 и перенести файлы
	- Только приложение: запустить Docker-образ на VPS, база пока остаётся в Supabase (VPS в том же регионе, рядом с базой)
	- Только база: перенести PostgreSQL, поменять строку подключения
	- Всё сразу — по шагам ниже
- **Какой сервер нужен на старте (по умолчанию)**
	- Один VPS: 4 ядра, 8 ГБ памяти, 160 ГБ диска, Ubuntu 24.04 LTS — приложение, worker, PostgreSQL, MinIO
	- Второй, маленький сервер или R2 — только для резервных копий
	- Позже, при росте, PostgreSQL переносится на отдельный сервер
- **Шаги переезда**
	1. За неделю: уменьшить время жизни DNS-записей в кабинете cctld.kg до минимального, если это можно настроить
	2. Подготовить VPS: Docker, Caddy, файрвол (открыты только 80, 443 и SSH по ключу), пользователь без root
	3. Скопировать `docker-compose.prod.yml` и файл переменных окружения; запустить пустую копию и прогнать проверку «здоровья»
	4. Перенести файлы: `rclone sync` из Supabase S3 в MinIO — заранее, затем ещё раз в окно переезда только изменения
	5. Окно переезда (ночь, около 30–60 минут): включить режим «Идут технические работы», остановить запись, `pg_dump` из Supabase → `pg_restore` на VPS, повторный `rclone sync`
	6. Проверить: число записей по таблицам совпадает, тесты приёмки проходят на VPS, вход и скачивание файла работают
	7. Переключить записи DNS в кабинете cctld.kg на адрес VPS; заново задать вебхук Telegram на новый адрес
	8. Выключить Vercel Cron, включить worker
	9. Две недели держать Vercel и Supabase в режиме «только чтение» как запасной вариант, затем отключить
- **Репетиция переезда** — по той же инструкции на тестовом стенде до первого выпуска и затем раз в квартал **(по умолчанию)**
- Инструкция переезда лежит в репозитории `docs/migration-vps.md` и обновляется вместе с кодом

##### Что меняем в ранее принятом стеке

- **Подробно и простыми словами**
	- О чём вообще вопрос
		- Сервисы остаются те же: Vercel, Supabase, Next.js, Hono; бюджет тот же; экраны и функции те же
		- Вопрос только в том, как писать код: чтобы при переезде на свой сервер его не пришлось переписывать
		- Сравнение: можно снять квартиру и пользоваться мебелью хозяина — удобно, но при переезде мебель остаётся, и на новом месте всё покупать заново; а можно сразу жить со своей мебелью — при переезде её просто перевозят
		- У Supabase и Vercel есть «мебель хозяина» — свои удобные встроенные части; если код на них опирается, при переезде эти места переписываются; мы предлагаем пользоваться только тем, что есть на любом сервере
	- Есть и другой путь: установить сам Supabase на свой VPS (у него открытый код)
		- Тогда код можно не менять, но на сервере придётся держать около десяти программ Supabase вместо двух (PostgreSQL и хранилище файлов), нужен сервер мощнее, а обновлять и чинить это сложнее
		- Поэтому рекомендую путь «своя мебель»: на сервере после переезда нужны только PostgreSQL и хранилище файлов MinIO
	- **Поправка 1. Вход в систему**
		- Что это: экран «Логин и пароль», проверка пароля, «Забыли пароль?» с кодом в Telegram, блокировка после неверных паролей, выход со всех устройств
		- Вариант «мебель хозяина»: пользоваться готовой системой входа Supabase (Supabase Auth)
			- Плюс: быстрее на старте примерно на 1–2 дня работы
			- Минусы для нашего ТЗ
				- Supabase Auth рассчитан на вход по почте или телефону; у нас вход по логину без почты и восстановление через Telegram, поэтому пришлось бы придумывать каждому служебный адрес вида login@buhuchet.local и обходить письма Supabase
				- Пароли сотрудников хранились бы в отдельной служебной части Supabase, а правила «кто какие данные видит» опирались бы на ключи Supabase
			- Что будет при переезде: либо ставить на VPS систему входа Supabase, либо переписывать вход и правила доступа; в худшем случае все сотрудники всех организаций заново задают пароли
		- Вариант «своя мебель» (рекомендую): свой вход
			- Логины и зашифрованные пароли лежат в нашей таблице в той же базе, что и контрагенты и отчёты
			- После входа браузер получает «пропуск» (сеанс), который выдаёт и проверяет наш сервер
			- Всё, что написано в ТЗ про вход (логин без почты, код в Telegram, 3 кода в час, блокировка, временный пароль от владельца), делается ровно как в ТЗ, без обходных путей
			- Что будет при переезде: база копируется целиком, вместе с логинами и паролями; сотрудники ничего не замечают и входят со старыми паролями
	- **Поправка 2. Файлы**
		- Что это: квитанции, свидетельства, выписки, файлы «Файлового менеджера», загруженные Excel-файлы
		- Где лежат: в Supabase Storage — это не меняется
		- Вопрос в том, как код с ним разговаривает; у Supabase Storage два «разъёма»
			- Свой фирменный разъём (библиотека Supabase): работает только с Supabase; при переезде каждое место в коде, где файл загружается, скачивается или удаляется, переписывается
			- Общий разъём S3 — стандарт, который понимают почти все хранилища: Supabase Storage, MinIO на своём сервере, Cloudflare R2, Amazon S3
		- Сравнение: зарядка с обычным разъёмом USB-C подходит к любому телефону, фирменная — только к одному
		- Рекомендую общий разъём S3: при переезде в настройках меняются четыре значения (адрес хранилища, ключ, секрет, название папки), сами файлы копируются программой rclone, код не трогаем
	- **Поправка 3. Серверная часть (API)**
		- Что это: часть системы, которая принимает действия из браузера и Telegram, проверяет права, пишет в базу, отправляет напоминания
		- Next.js умеет держать и экраны, и серверную часть в одной программе; на Vercel это удобно
		- Вариант «мебель хозяина»: серверный код разбросан по страницам Next.js с использованием особых возможностей Next.js и Vercel
			- При переезде это работает только внутри Next.js; отделить сервер от сайта или запустить его на другой машине — значит переписывать
		- Вариант «своя мебель» (рекомендую): весь серверный код — в отдельной папке-пакете на Hono, а Next.js только «подключает» его одним файлом
			- Сейчас на Vercel всё работает одной программой, как и было в ТЗ
			- На VPS можно запустить так же одной программой или разделить: сайт отдельно, сервер отдельно
			- Тот же сервер потом можно отдать мобильному приложению или другому сервису без переделок
	- Что вы получаете, если согласны
		- Переезд на VPS — работа на один вечер по инструкции (раздел «Переезд на VPS/VDS»), без переписывания кода и без смены паролей сотрудникам
		- Дополнительно примерно 1–2 дня разработки на старте (свой вход); денег сверху — ноль
	- Что будет, если не согласны
		- Старт на 1–2 дня быстрее
		- При переезде — либо ставить Supabase целиком на свой сервер, либо переписывать вход, работу с файлами и часть сервера; по оценке — от одной до нескольких недель работы и риск ошибок при переезде
	- Вы согласились 21.10.2026; раздел ТЗ «Основные технические парадигмы → Стек» переписывается под эти три поправки
- **Вход: свои сеансы вместо JWT Supabase**
	- Сейчас в ТЗ: сеанс как JWT, подписанный ключом Supabase, чтобы работали политики Supabase
	- Почему меняем: это привязывает вход к ключам и функциям Supabase; при переезде пришлось бы переделывать вход и все политики
	- Как будет: свои сеансы в базе, политики RLS по `app.org_id`; браузер к базе всё равно не ходит, так что ничего не теряем
- **Хранилище файлов только через протокол S3**
	- Supabase Storage остаётся, но код работает с ним как с любым S3, без библиотеки Supabase; при переезде меняются только адрес и ключи
- **API — отдельный пакет, а не код внутри Next.js**
	- Остаётся Hono и один catch-all роут; но сам код API лежит в отдельном пакете и может работать без Next.js
- **Задачи по расписанию не зависят от Vercel Cron**
	- Vercel Cron только «дёргает» маршрут; вся логика и очередь — в нашем коде и в PostgreSQL
- Остальное без изменений: Next.js, Hono с Zod, PostgreSQL, бюджет около 45 $ в месяц; Cloudflare в первом выпуске не нужен (ваш ответ 21.10.2026)
	- Vercel Pro около 20 $ за участника в месяц; Supabase Pro около 25 $ (8 ГБ базы и 100 ГБ файлов входят) **(по умолчанию; цены уточнить на сайтах перед оплатой)**
	- Тестовый стенд — отдельный проект Supabase Free и превью Vercel, без доплаты **(по умолчанию)**
